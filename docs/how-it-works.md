# Как принимаются решения

## Проба

Для каждого моста сторож собирает минимальный конфиг xray: локальный HTTP-инбаунд на
`127.0.0.1:<port_base + номер моста>` → VLESS-outbound на `ip:probe.port` с Reality
(`sni`, `public_key`, `short_id`, `fingerprint`, `flow`). Через этот прокси открываются
`probe.urls` по очереди; проба успешна, если в ответе есть IPv4-адрес.

Это путь клиента целиком: TLS-рукопожатие Reality на мосту → правила маршрутизации
моста → выходная нода → интернет. Если сломано любое звено — проба провалится.
Мосты проверяются параллельно, весь прогон занимает несколько секунд.

## Счётчики и гистерезис

У каждого моста в состоянии (`/var/lib/bridge-guard/state.json`) три поля:
`fails` (провалов подряд), `oks` (успехов подряд), `dead`.

- живой мост и `fails ≥ fail_n` → **умер** (событие `died`);
- мёртвый мост и `oks ≥ ok_n` → **ожил** (событие `revived`).

Одиночный провал (дрогнула сеть, перегружен выход) ничего не переключает. С таймером
раз в минуту и `fail_n = 3` реакция занимает три минуты; если мост «мигает» — часть проб
проходит, — счётчик сбрасывается, и решение откладывается. Это осознанно: лучше
лишняя минута, чем дёрганый пул.

## Действия при событии `died`

1. **DNS-пул** (`failover.dns`): из A-записей имени убираются записи с IP моста.
   Не убираются, если после этого в пуле останется меньше `min_pool` записей.
2. **Хосты подписки** (`failover.hosts`): все хосты панели с адресом `match_address`
   переводятся на IP первого живого моста. Перед правкой сохраняется копия всех хостов.
   Повторно не переключается, пока не вернули.
3. Сообщение в Telegram со списком живых мостов.

Если живых мостов нет — только сообщение. Переключать некуда, и портить пул незачем.

## Действия при событии `revived`

1. A-запись моста возвращается в DNS (TTL из конфига, `proxied: false`).
2. Если все мосты живы и хосты были переведены — они возвращаются на `match_address`.
   Если мёртвые ещё есть — хосты остаются на живом IP, об этом сказано в сообщении.

## Заморозка (`max_dead`)

Если после прогона мёртвых мостов больше `max_dead` и среди них есть новые — сторож
считает, что проблема на его стороне (сеть хоста, фильтр, упавший Xray), а не у мостов:
автодействия останавливаются, приходит 🟠-сообщение. Счётчики продолжают считаться.
Как только мёртвых снова не больше `max_dead`, заморозка снимается, и для мостов,
умерших во время заморозки, действия выполняются.

Для двух мостов `max_dead = 1` означает: «оба мертвы» = не трогать ничего.
Для пула из десяти мостов разумно `max_dead = 3–4`.

## Репетиция отказа

`bridge-guard --dry-run --fake-dead RF-2` считает мост RF-2 мёртвым сразу (без ожидания
`fail_n`) и печатает всё, что сделал бы сторож: какую запись убрал бы из DNS, какие хосты
и куда перевёл бы, какое сообщение отправил. Ни DNS, ни хосты, ни состояние при этом не
меняются. Так можно проверить конфиг и права токенов до первого настоящего отказа.
`--fake-dead` без `--dry-run` переключает по-настоящему — сторож об этом предупредит.

## Состояние и откат

`state.json` хранит счётчики, флаг заморозки и что именно было переключено
(`switched`: куда, какие хосты, когда, где бэкап). Удалить файл — сторож начнёт с чистого
листа, считая все мосты живыми; переведённые хосты при этом останутся переведёнными —
верните их из бэкапа или руками.

Ручной откат в любой момент безопасен: вернули A-запись и адреса хостов — при следующем
прогоне сторож увидит живой мост и не будет ничего перекраивать.

## Коды выхода

`0` — все мосты живы, `1` — есть мёртвые (штатно для таймера, `SuccessExitStatus=0 1`),
`2` — ошибка конфигурации или панели.
