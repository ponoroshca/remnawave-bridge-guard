# Настройка панели

Всё, что ниже, делает `bridge-guard setup` — здесь описано, что именно он делает и как
сделать то же самое руками, если хочется контролировать каждый шаг.

Мастеру нужен API-токен панели. Заведите отдельный (Remnawave → API Tokens), чтобы
отозвать его независимо от остальных. Сторожу от панели нужны: чтение профилей, нод,
сквадов и хостов; изменение адреса хостов; создание одного пользователя.

Сторожу нужны три вещи: служебный пользователь, параметры Reality-инбаунда мостов и
(по желанию) DNS-пул с токеном.

## 1. Служебный пользователь

В панели создайте пользователя, например `bridge-probe`, с длинным сроком и без лимита
трафика (проба тратит килобайты). Добавьте его во внутренний сквад, который привязан к
инбаунду мостов, через который ходят клиенты (обычно режим «Авто»). Если пользователь не
состоит в сквадах инбаунда — мост честно отвергнет его, и сторож будет считать мост мёртвым.

В конфиг идёт **`vlessUuid`** пользователя (в API — поле `vlessUuid`, не `uuid` записи).
Взять можно из карточки пользователя или запросом:

```bash
curl -s -H "Authorization: Bearer $TOKEN" "https://panel.example.com/api/users?size=500" \
  | python3 -c "import sys,json; [print(u['username'], u['vlessUuid']) for u in json.load(sys.stdin)['response']['users'] if u['username']=='bridge-probe']"
```

## 2. Параметры Reality

Нужны `public_key`, `short_id` и `sni` инбаунда мостов. Проще всего взять их из ссылки
подписки любого пользователя того же сквада: `pbk=`, `sid=`, `sni=`. Либо из профиля:
приватный ключ лежит в `streamSettings.realitySettings.privateKey`, публичный считается
командой `xray x25519 -i <privateKey>` (бинарник — `/opt/bridge-guard/xray`).

`fingerprint` и `flow` — как у клиентов (`firefox`/`chrome`, `xtls-rprx-vision`).

## 3. DNS-пул

Один хост подписки с адресом-именем (например `bridge.example.com:2053`) и несколько
A-записей этого имени — по одной на мост, TTL 60, без проксирования Cloudflare (серый
облак). Клиенты получают адреса по кругу; сторож убирает из пула мёртвые.

Токен Cloudflare: *My Profile → API Tokens → Create Token → Edit zone DNS*, зона — одна.
Положите его в файл:

```bash
install -m 600 /dev/null /etc/bridge-guard/cloudflare.token
nano /etc/bridge-guard/cloudflare.token
```

## 4. Режим хостов (без DNS или вместе с ним)

Если адреса мостов прописаны в хостах подписки напрямую, укажите в `failover.hosts.match_addresses`
адреса, по которым сторож их находит (имя пула и/или IP мостов). При смерти моста
эти хосты получат IP живого моста, клиенты — при автообновлении подписки
(`profileUpdateInterval` в шаблоне подписки; час — разумное значение).

Для этого режима нужен API-токен панели (`panel.token`) — заведите отдельный, чтобы его
можно было отозвать независимо от остальных.

## 5. Проверка

```bash
bridge-guard doctor
bridge-guard run --dry-run
```

Каждый мост должен показать `ок`. Если `ПРОВАЛ` у всех — почти всегда дело в служебном
пользователе (не в сквадах инбаунда) или в ключах Reality. Проверьте проще:
`lanes-probe --bridge <имя или ip>` покажет по каждому инбаунду отдельно.
