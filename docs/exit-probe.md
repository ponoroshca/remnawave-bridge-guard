# exit-probe — достижимость выходных нод с моста

## Зачем

Панель смотрит на ноду из-за границы и видит её живой. Клиент идёт через мост, и именно
с моста нода может быть недоступна. Пинг при этом проходит — ТСПУ режет TCP, а не ICMP.
Поэтому зонд проверяет **TCP-коннект на рабочий порт** каждого выходного outbound'а.

## Как ставится

С хоста сторожа, где уже настроен `/etc/bridge-guard/config.json` (нужны `panel.*`
и `telegram`):

```bash
./scripts/install-exit-probe.sh <ip-моста> "<имя профиля мостов>" <имя-моста> [ssh-ключ]
```

Скрипт собирает конфиг из живого профиля панели (`exit-probe-conf`), копирует зонд и
юниты на мост, включает таймер (раз в 30 минут) и показывает пробный прогон.

Outbound'ы с `proxySettings` (ходят через другой outbound) в список не попадают —
напрямую с моста они и не должны открываться.

**После смены адреса любой ноды** запустите установку заново — список статичный.

## Что означают сообщения

| контроль (заграница / РФ) | вывод | что чинить |
|---|---|---|
| ✗ / ✓ | **отрезан сам мост** | новый или дополнительный IP у моста |
| ✗ / ✗ | у моста нет сети | связь, маршрут, файрвол моста |
| ✓ / ✓, нода ✗ | проблема ноды | если и с другого моста ✗, а снаружи РФ ✓ — блокировка по IP ноды |

Контрольные точки по умолчанию: Cloudflare `104.16.123.96:443` (заграница) и
`ya.ru 77.88.55.242:443` (РФ). Для другой страны замените `controls` в конфиге на
пару «крупный зарубежный : крупный местный».

## Повторы

Одна и та же проблема — одно сообщение в `repeat_hours` (6 по умолчанию). При фильтре на
мосту набор упавших нод дребезжит (часть соединений проскакивает), поэтому такие случаи
считаются одной проблемой независимо от списка.

## Вручную

```bash
python3 /opt/exit-probe/exit_probe.py --force --quiet    # отчёт в консоль, без Telegram
python3 /opt/exit-probe/exit_probe.py --force            # отчёт в Telegram, даже если всё хорошо
```
